# Project update audit and implementation plan

Audit date: 6 November 2026 (Asia/Shanghai). Original scope: Step 1 audit; current completion checklist added by Step 12, based on `Problem for update.txt`, `propmt_for_project_update.md`, runnable source, SQL migrations, templates/assets, tests and read-only inspection of the configured PostgreSQL database.

## Scope, interpretation and evidence standard

- The intended two public entry points are **`/` for the shared marketplace** and **`/admin-app/` for administration**. Nested buyer/seller workflows are permitted; this does not mean only two URLs.
- There must be one provisioned administrator, sign-in only, with no public administrator registration. The contradictory account-creation sentence in the source is resolved by the explicit Step 1 instruction. Credentials in the source are intentionally omitted here.
- “Open any account” means authorized inspection of account information, not impersonation, password bypass, session switching or disclosure of password hashes.
- “Change roles/rules” means explicitly supported marketplace policies and controlled memberships, not unrestricted SQL, arbitrary privilege elevation or editing immutable history. Administrative and marketplace identities are currently disjoint.
- AI output is advisory risk, not a fraud verdict. Threshold changes normally require rescoring; changes to predictor semantics/training configuration or eligible labels can require retraining. Do not fit models for unrelated moderation or appearance changes.
- **Present** below means implemented in inspected source, not newly verified end to end. **Partial**, **Missing**, **Mismatch**, and **Operational gap** distinguish unfinished behavior from requirements changes and deployment state. Checklist boxes remain open until later steps have fresh acceptance evidence.
- No application/database mutation, provisioning, migration, scan, training, seed or test-data creation was performed. This Markdown plan is the only intended repository addition. No browser inspection was performed.

## Database, migration and operational findings

### Installation authority and retained invariants

`docs/MIGRATIONS.md` makes Django migrations authoritative. `accounts/0001_initial` owns identity/auth mapping; `marketplace/0001_initial` loads frozen SQL 001–005 and unmanaged domain state; `risk/0001_initial` records risk mappings. Marketplace 0002 adds rate limits/groups/categories, 0003 private listing drafts with separate database/state operations, and 0004 reviewed-export SQL helpers. `database/install.sql` and reference scripts are a separate installation/test path, never an upgrade overlay.

Inspected SQL in `marketplace/migrations/sql/001_core.sql` through `006_admin_exports.sql` provides:

- Lowercase-email uniqueness plus identity/status checks; disjoint administrator vs buyer/seller memberships, but no administrator singleton constraint. `UserManager.create_superuser` directs operators to provisioning.
- Product/revision composite primary and foreign keys, deferred current-revision reference, immutable revisions/images, positive finite prices and valid conditions. Revisions/images and order snapshots must remain intact.
- Buyer-scoped request-key uniqueness, a partial unique non-cancelled product-order index, guarded order transitions, reservation/sold behavior and append-only order events.
- Report/revision/order consistency, terminal report timestamps, private evidence associations, canonical append-only review correction chains and immutable audits.
- One active model and ruleset via partial unique indexes; schema compatibility, immutable registered metadata, frozen datasets and point-in-time predictor chronology.
- Deduplicated revision/context/model/rules scan jobs, one log per job, bounded attempts, claim token/lease/fencing, resumable rescan campaigns and freshness-aware read views. Preserve these when adding publication/training states.
- Existing `seller_appeals` is review-specific with pending/reviewing/upheld/corrected/withdrawn states and one open appeal per review; it cannot represent all account-block appeals or their proof attachments without extension.
- Existing indexes cover full-text revision search, category/price, condition/location, orders, reports, messages, audit targets and scan/campaign queues. Add indexes for new query patterns, not duplicate equivalents.

### Defects, dependencies and design traps

1. **Publication order is the largest behavioral mismatch:** current public availability precedes scanning. Merely hiding pending badges or waiting in JavaScript would not implement scan-before-publication. Update submission triggers, feature extraction, current-risk views, public queries and purchasing together. In particular, feature extraction currently relies on first-publication chronology; an unpublished submission needs a valid snapshot path without circularly requiring publication before it can be scanned.
2. **Existing requested admin identity cannot be blindly promoted:** it already exists, the provisioning command refuses existing emails, and marketplace/admin memberships are disjoint. Inspect its memberships and retained relationships privately in Step 4, establish an explicit audited transition/recovery procedure, and preserve the sole working administrator until the replacement path is verified. Do not guess that removing membership makes all historical participant operations compatible with admin isolation.
3. **Demo provisioning conflicts with a singleton policy:** seed logic currently creates a separate demo administrator. Adapt it rather than allowing a second administrator or altering real credentials.
4. **Configured owner connection bypasses intended runtime separation.** Migrations being applied does not establish privilege hardening. New feature verification must include actual restricted process logins.
5. **Existing appeals are not account-block appeals.** Do not repurpose review decisions or map “upheld” ambiguously to unblock approval. Preserve existing review appeal semantics.
6. **Rule editing is narrower than the source request.** Score bands affect classification/rescoring; predictor semantics and keyword sets belong to immutable feature-schema versions. Changing their meaning under `marketplace-v1` would break reproducibility and worker compatibility.
7. **Evaluation exists without automatic quality gating.** Checksums and valid metrics are integrity checks, not evidence of adequate model quality. Synthetic results cannot establish real-world accuracy.
8. **Profile edits can change feature inputs.** Location updates need documented context invalidation/rescan behavior while frozen historical features/order snapshots remain unchanged.
9. **Historical documents conflict with the update.** `PRD.md` and `ARCHITECTURE.md` describe three entry points; the architecture introduction also says implementation is only proposed despite runnable code. Treat update instructions as current scope and reconcile documentation in Step 12.
